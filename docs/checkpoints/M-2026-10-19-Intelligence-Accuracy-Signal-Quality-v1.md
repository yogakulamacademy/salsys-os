# M-2026-10-19 — Intelligence Accuracy / Signal Quality V1

## Goal

Make Salsys intelligence more accurate under privacy constraints by separating **missing evidence** from **negative evidence** and by preventing privacy-restricted subjects from entering the predictive feature-snapshot pipeline.

This checkpoint does **not** claim that a model is accurate. Accuracy claims remain blocked until enough realized outcomes exist for holdout calibration and live drift evaluation.

## Why this checkpoint exists

The existing R10 predictive foundation is already conservative in important ways:

- deterministic ranking scores are not presented as calibrated probabilities;
- model promotion requires holdout quality and calibration guardrails;
- predictions support confidence bounds, reason codes, explanations and realized outcomes;
- temporal leakage checks exist for lead-model training data.

A remaining accuracy risk was that absent numeric web signals could be represented as zero. Under consent-aware tracking, zero and unknown are not the same:

```text
0 page views observed       = observed evidence
no page-view evidence       = unknown / unavailable evidence
```

Treating both as zero can systematically underestimate intent for visitors who do not permit analytics or whose journey cannot be linked confidently.

## Added

### Consent-aware signal-quality view

`public.v_r10_lead_signal_quality_v1`

For each lead it evaluates:

- linked person identities;
- linked anonymous visitors and sessions;
- current analytics preference evidence across lead/person/visitor privacy subjects;
- active processing/profiling/optional-tracking restrictions;
- whether web behavior is usable for profiling;
- identity evidence state;
- evidence-quality band and reason codes.

The view deliberately fails closed when choices are mixed or when profiling/processing is restricted.

### Safe V2 feature snapshots

`app/api/intelligence/lead-scoring-snapshot/route.ts` now writes:

```text
r10-lead-features-safe-v2
```

Guardrails:

- privacy-restricted leads are skipped;
- terminal leads are still not snapshotted after outcome;
- labels still apply only to observations strictly before the outcome;
- web behavior is used only when signal quality marks it usable;
- missing or withheld web evidence is stored as `null`, not fabricated as zero;
- CRM/transaction context remains separate from web observability;
- no probability is generated by the snapshot collector.

Every safe snapshot now contains explicit `feature_availability` and `evidence_quality` metadata.

### Safe V2 training dataset

`public.v_r10_lead_training_dataset_safe_v2`

This dataset:

- includes only realized binary outcomes (`positive` / `negative`);
- requires observation time to be strictly earlier than outcome time;
- includes only snapshots where profiling was allowed;
- preserves missing numeric evidence as NULL;
- exposes web-behavior availability, analytics evidence state and evidence-quality metadata.

The legacy R10 dataset is not silently rewritten. This creates an explicit migration boundary for future model versions.

### Safe V2 training readiness

`public.v_r10_lead_model_training_readiness_safe_v2`

Candidate training remains blocked until at least:

- 40 distinct labeled leads;
- 20 positive leads;
- 20 negative leads;
- zero temporal leakage violations.

Meeting these thresholds only permits candidate-model work. It does not permit production probability claims without holdout calibration and promotion guardrails.

### Accuracy-learning health

`public.v_intelligence_accuracy_health_v1`

Reports evidence collection/readiness without manufacturing an accuracy percentage. It distinguishes states such as:

```text
collecting_leads
collecting_privacy_aware_features
collecting_realized_outcomes
ready_for_candidate_model_work
observing_probability_accuracy
outcome_learning_active
```

It also separates deterministic ranking-score predictions from probability predictions.

## CI protection

Added:

```text
npm run verify:intelligence-accuracy
```

CI verifies that:

- the privacy-aware signal-quality view exists;
- profiling permission is explicitly checked;
- mixed/unknown analytics states remain fail-closed;
- safe V2 training data exists;
- realized binary outcomes and point-in-time ordering are required;
- the snapshot route cannot silently restore the old missing-number-to-zero helper.

## Accuracy principles locked by this checkpoint

1. Missing data is not negative behavior.
2. A ranking score is not a probability.
3. Privacy restrictions are upstream of profiling/model features.
4. Observed facts and inferred scores remain separate.
5. Model accuracy is measured against realized outcomes, never asserted from implementation alone.
6. PostgreSQL remains authoritative; derived/search projections do not become model truth.
7. No fingerprinting or weak-identity workaround is introduced to compensate for consent loss.

## Production acceptance remaining

After merge, apply the migration and run a controlled snapshot collection. Verify:

1. restricted leads are skipped;
2. leads without usable analytics evidence receive NULL web features rather than zeros;
3. permitted web evidence remains present when available;
4. positive/negative labels attach only to pre-outcome snapshots;
5. `v_intelligence_accuracy_health_v1` reports observed counts honestly;
6. no production probability model is activated merely because this checkpoint is deployed.

The next intelligence checkpoint should focus on **realized-outcome collection + calibration/drift learning**, after safe V2 evidence begins accumulating.
