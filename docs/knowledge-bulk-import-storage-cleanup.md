# Storage cleanup and quota recovery (review only)
Extends existing review ledger/reservation, not a migration. Owner-only begin/complete storage cleanup functions: terminal job, retention deadline passed, no pending/leased entries, exact registered path/version/digest; stable cleanup ID, matching evidence digest and atomic quota release. Retained bytes remain charged before receipt; reserve and release serialize on per-tenant quota row. Duplicate exact receipt is idempotent, changed evidence rejects; created Knowledge drafts and ledger/history remain intact. Unversioned abandoned reservations remain charged pending separate proven absence protocol. SQL cannot independently verify provider deletion; external evidence must be produced by a separately approved, restricted cleanup broker, bind actual deletion/absence and quiescence of every pending TUS upload/replay, and be retained under approved audit policy. No actual provider cleanup or grants implemented. Supabase requires Storage API deletion rather than SQL removal of storage.objects (https://supabase.com/docs/guides/storage/management/delete-objects); never delete metadata directly. Verify provider retention, active signed URLs, immutable no-recreation policy, and stale uploads before granting any cleanup execution. The review owner is privileged, not an acceptable production worker identity. CI tests use synthetic evidence, exercise no early release, wrong identity, rollback, concurrent replay, quota reuse and draft preservation. Prior connected fixture and capacity step passed; latest revision untested. No hosted SQL, storage deletion, provisioning, migration, merge or deployment.
