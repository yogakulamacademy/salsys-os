# Knowledge import phase 3 — transactional processing contract (review only)
This is an offline lifecycle model, not a worker or database transaction. No calls to Storage, Supabase, provider APIs or model. Existing importer and Option A boundary unchanged. SQL ledger draft remains outside migrations. Default retry schedule and 120-second leases are engineering proposals; tune from synthetic performance tests. No hosted execution authorized.

## State and atomicity
Use one verified immutable object and one job id; preflight outputs exactly one disposition for every original index (pending/invalid/duplicate). Reject inconsistent partition, over-limit manifest, expired reservation or digest mismatch. Bind to authenticated actor/session/org and immutable object version. Real server derives scope; never accept client authority. Job reservation and quota count must be transactional. Enqueue locks job row by organization+id, verifies current authority and exact digest, inserts complete disposition ledger and changes job status atomically. Repeated identical enqueue returns existing result; inconsistent manifest fails. Record a manifest fingerprint and per-entry normalized content hash in the eventual migration; this model does not calculate them.

## Proposed SQL transaction sequence (not executable SQL)
All transitions lock the same tenant/job parent first to serialize cancellation, expiry, enqueue and finalization, then lock exact entry rows in ascending index order. Authorize current user/session or separately reviewed constrained worker delegation in the same transaction; service_role alone is not authorization. Claim up to 50 entries using due time and expired leases; use database time, unique lease tokens, attempt counter, and bounded lease. Retry only classified transient failures; default backoff 30,60,120,240 seconds, max five attempts. Expired fifth lease becomes failed. Revalidate lease+attempt+tenant+job state on every settle. For real worker content fetch, verify immutable raw object hash and normalized row hash; no URL fetching from source_uri.

Atomic finalize outline:
1. Begin transaction; lock parent, then exact entry; check current delegated actor authority, lease token, attempt, expiry, cancellation, and source/manifest identity.
2. If already created, return existing document id for the same authenticated entry (no second write); reject stale or mismatched claims.
3. Invoke existing create_source_backed_knowledge_document_v2 with hard-coded p_approve=false in this transaction; do not accept approval parameters from the manifest. Verify returned document_id and draft status against tenant-bound persisted document. Review existing RPC actor attribution: auth.uid() may be null under service_role; do not ship worker until named actor attribution and delegated authority are solved.
4. Update entry to created with document_id, clear lease, derive job terminal status/counts from locked ledger. Commit. Any exception or unexpected result must roll back both Knowledge creation and ledger update. Unique organization+document_id and organization+job+index constraints prevent inconsistent mapping, not cross-file content duplication.
5. On transient failure, retry in a separate transaction only after confirming original transaction did not commit. Unknown outcome: read durable entry before retry. No blind rerun. On cancellation/expiry, preserve completed drafts, invalidate outstanding leases and cancel pending rows in same parent-locked transaction. Progress counts terminal rows separately by created/invalid/duplicate/failed/cancelled; 100% processed is not 100% successful.

## Acceptance
Reference tests verify deterministic state behavior, not real locking or tenant isolation. Disposable PostgreSQL acceptance must prove two concurrent claims, concurrent cancel/finalize, expired/stale lease rejection, duplicate enqueue, rollback on injected failure after RPC and before ledger update, retry after lost commit acknowledgement, revoked authority, tenant mismatch, no approval, quota and retention enforcement. Verify RLS/grants, session delegation and object ACLs before runtime. No SQL migration, bucket, route, cron, worker or deployment in this checkpoint. Phase 1 #919 and P0 #917 remain separate; staging hold preserved.
